# Freshr Test Plan

**Codebase snapshot:** Django 6.0.1 · DRF 3.16 · Celery 5.6 · SimpleJWT · PGVector · Anthropic Claude Haiku · Google Gemini Embeddings · ZiniPay · React + TypeScript (Vite)

---

## 1. Critical Path Map

This maps the 20% of code that delivers 80% of user value. All paths are in the active URL surface (`presentation`, `quiz`, and `flashcard` are commented out of `freshr/urls.py` and excluded).

---

### CP-1 — User Registration & JWT Auth
**Priority: P0**

**User flow:** Visitor registers with email/password → receives JWT access + refresh tokens → uses access token for all subsequent requests.

**Files / functions involved:**
- `users/views.py` → `RegistrationView.post`
- `users/serializers.py` → `RegistrationSerializer.validate`, `RegistrationSerializer.create`
- `users/models.py` → `CustomUserManager.create_user`
- `freshr/urls.py` → `auth/register/`
- `freshr/settings.py` → `SIMPLE_JWT` config (60 min access / 1 day refresh)

**Failure modes:**
- Duplicate email not caught → IntegrityError or silent overwrite
- Password validation skipped (Django validators configured but can be bypassed with direct DB writes)
- JWT secret key hardcoded in settings (currently `django-insecure-...`) — tokens forgeable if same key used in production
- No email verification step: `is_active=True` by default, so any address can be used

---

### CP-2 — Login, Logout & Token Refresh
**Priority: P0**

**User flow:** User logs in → gets tokens → uses refresh token to get new access token before expiry → logs out by blacklisting refresh token.

**Files / functions involved:**
- `users/views.py` → `LoginView.post`, `LogoutView.post`
- `freshr/urls.py` → `auth/token/refresh/` (SimpleJWT built-in)
- `rest_framework_simplejwt.token_blacklist` (installed app)

**Failure modes:**
- `LogoutView` catches all exceptions and returns 400 — a malformed or already-blacklisted token returns an opaque error with no distinction
- No brute-force protection on `POST /auth/login/`
- `LoginView.post` calls `authenticate(username=email, password=...)` but the permission class is the DRF default (`IsAuthenticated` not set) — the view has no `permission_classes`, so it defaults to whatever `DEFAULT_AUTHENTICATION_CLASSES` says; an already-authenticated user can log in again with no guard
- `LogoutView` requires authentication but a stolen access token can be used to blacklist a victim's refresh token

---

### CP-3 — Google OAuth Sign-In
**Priority: P1**

**User flow:** User clicks "Sign in with Google" → frontend gets Google Access Token → `POST /auth/google-login/` → backend fetches userinfo from Google → creates/retrieves User → returns JWT tokens.

**Files / functions involved:**
- `users/views.py` → `GoogleAuth.post`
- `users/serializers.py` → `GoogleAuthSerializer`
- `users/models.py` → `User.objects.get_or_create`

**Failure modes:**
- Backend makes a live HTTP call to `https://www.googleapis.com/oauth2/v3/userinfo` — no mock in tests; network failures propagate to 400
- An attacker can call this endpoint with any valid Google access token belonging to someone else's account — no binding to the frontend OAuth client ID
- `registration_method` conflict check (email user tries Google login returns 403) is correct but the reverse — Google user trying email login — has no guard; `authenticate()` will just fail on unusable password, which is safe, but the error message leaks which method was used
- `get_or_create` is not atomic; concurrent first-time logins for the same email could create two User rows before the `unique` constraint fires

---

### CP-4 — Notebook CRUD
**Priority: P1**

**User flow:** Authenticated user creates a notebook → renames/pins it → deletes it (which cascades to files and triggers vector cleanup).

**Files / functions involved:**
- `notebooks/views.py` → `NotebookListAPIView`, `NotebookDetailAPIView`
- `notebooks/serializers.py` → `NotebookSerializer`
- `notebooks/models.py` → `Notebook`
- `notebooks/signals.py` → `cleanup_notebook_vectors` (post_delete)
- `rag/tasks.py` → `delete_notebook_vectors_task`

**Failure modes:**
- `NotebookDetailAPIView.get_object` uses `get_object_or_404(Notebook, pk=pk, user=request.user)` — correct ownership check
- `NotebookListAPIView` filters by `user=request.user` — correct
- Signal fires `delete_notebook_vectors_task.delay` even if Celery/Redis is down; the Notebook row is deleted but vectors may remain orphaned
- No limit on the number of notebooks per user (no quota enforcement)

---

### CP-5 — File Upload & Ingestion Pipeline
**Priority: P0**

**User flow:** User uploads a PDF or image to a notebook → file saved to disk → `ingest_note_task` dispatched to Celery → PDF partitioned by `unstructured` → chunked → optionally AI-summarised by Claude Haiku → embeddings generated by Gemini → stored in PGVector → `ingestion_status` set to `ready` (or `failed`).

**Files / functions involved:**
- `notebooks/views.py` → `NotebookFileCreateAPIView.post`
- `notebooks/services/notebook_file.py` → `NotebookFileService.add_notebook_file`
- `rag/tasks.py` → `ingest_note_task`
- `rag/services.py` → `ingest_note_to_rag`, `get_vector_store`, `separate_content_types`, `create_ai_enhanced_summary`

**Failure modes:**
- `ingest_note_task` wraps an `asyncio.run()` call inside a Celery worker — if the worker process already has a running event loop (e.g., gevent/eventlet worker mode) this raises `RuntimeError: This event loop is already running`
- No file type allowlist beyond splitting on `.` — `file_type = file_name.split(".")[-1]` — a file named `exploit.pdf.sh` gets `file_type = "sh"`, which then raises `ValueError: Unsupported file type` inside the Celery task (safe but not graceful)
- No file size limit enforced in the view or serializer
- `ingest_note_to_rag` raises `ValueError` for unsupported types, setting `ingestion_status = FAILED` — but the task re-raises, meaning Celery will retry (if configured), potentially generating double vectors on retry after a partial run
- `_vectorstore_table_initialized` is a module-level global — in a multi-worker Celery deployment each worker initializes independently, causing multiple concurrent `ainit_vectorstore_table` calls; the `except ProgrammingError: pass` suppresses conflicts but is fragile
- AI summarisation failures fall back to raw text (good), but the fallback is silent — no monitoring or alerting surface

---

### CP-6 — RAG Chat (Streaming LLM Response)
**Priority: P0**

**User flow:** User opens a chat → sends a message → `POST /chats/{id}/messages/` creates a user `ChatMessage` → `GET /chats/{id}/messages/stream/` triggers RAG retrieval against PGVector → builds system prompt → streams Claude Haiku response as SSE → bot `ChatMessage` persisted at stream end.

**Files / functions involved:**
- `chats/views.py` → `ChatMessageListCreateView.perform_create`, `ChatMessageStreamView.get`
- `chats/services/rag_retrieval_service.py` → `get_notebook_context`, `build_study_assistant_prompt`
- `chats/services/llm_service.py` → `_stream_llm_response`
- `rag/services.py` → `query_notebook_rag`
- `chats/models.py` → `Chats`, `ChatMessages` (unique_together on `(chat, order_index)`)

**Failure modes:**
- `get_notebook_context` calls `asyncio.run(query_notebook_rag(...))` — will raise `RuntimeError` if called from inside an existing async context (e.g., Django's async views or ASGI)
- `order_index = ChatMessages.objects.filter(chat=chat).count()` is a race condition: two concurrent message POSTs will both read the same count and hit the `unique_together` IntegrityError
- If `_stream_llm_response` generator raises before the `ChatMessages.objects.create(...)` call (e.g., Anthropic API error mid-stream), the bot turn is never persisted but the user message is — leaving the chat in an inconsistent state
- `ChatMessageStreamView` is a GET request that creates side effects (persists a bot message) — not idempotent; double-requesting the same stream creates duplicate bot messages
- Streaming response with `StreamingHttpResponse` disables Django's exception middleware — errors mid-stream are yielded as `data: {"error": "..."}` SSE events, not HTTP error responses; the frontend must handle this

---

### CP-7 — Payment & Subscription Activation
**Priority: P1**

**User flow:** User clicks "Subscribe" → `POST /payments/initiate/` creates a pending Payment row and calls ZiniPay API → frontend redirects to ZiniPay → ZiniPay sends webhook to `POST /payments/webhook/` on completion → Account tier upgraded to PAID and subscription dates set.

**Files / functions involved:**
- `payments/views.py` → `InitiatePaymentView.post`, `ZiniPayWebhookView.post`
- `payments/models.py` → `Payment`
- `accounts/models.py` → `Account` (tier_plan, subscription_status, subscription_start/end_date)

**Failure modes:**
- **No webhook signature verification** — `ZiniPayWebhookView` accepts any POST with a valid `payment_id` in metadata; an attacker who knows or guesses a `payment_id` (UUID, so hard to guess, but still) can forge a webhook and upgrade any account for free
- The webhook endpoint is `@csrf_exempt` and has `authentication_classes = []`, `permission_classes = []` — intentional for external webhooks, but the lack of signature verification is critical
- `Payment.objects.create(amount=amount, ...)` before the ZiniPay call — if ZiniPay call fails, a `PENDING` payment row is created but never cleaned up (status set to FAILED, but row remains)
- No idempotency check: replaying the same `COMPLETED` webhook will call `account.save(...)` again, unnecessarily (harmless but wasteful and could cause issues if subscription_end_date is recalculated)
- `Account.DoesNotExist` returns 404 to the user, but leaks that the endpoint requires an Account — users without an Account (no onboarding) cannot subscribe
- Subscription expiry is never automatically enforced — no Celery periodic task to flip `ACTIVE` → `EXPIRED` when `subscription_end_date` passes

---

### CP-8 — Account Onboarding & Profile
**Priority: P2**

**User flow:** New user completes onboarding → `POST /users/accounts/` creates Account record with name/address → user can `PATCH /users/accounts/me/` to update profile.

**Files / functions involved:**
- `accounts/views.py` → `AccountListAPIView`, `AccountDetailAPIView`
- `accounts/serializers.py` → `AccountSerializer`

**Failure modes:**
- **`AccountListAPIView` has no ownership filter** — `queryset = Account.objects.all()` — any authenticated user can `GET /users/accounts/` and see every account in the database. This is a data exposure bug.
- `AccountListAPIView.perform_create` calls `serializer.save(user=self.request.user)` — the `user` field FK is set correctly, but there is no uniqueness constraint preventing a user from creating multiple Accounts (only the `OneToOneField` on the model itself enforces this at the DB level, which would raise IntegrityError rather than a clean validation error)

## 4. Frontend Test Breakdown

The frontend is React + TypeScript (Vite). No test framework is currently configured — recommended setup is **Vitest** + **React Testing Library** for components/hooks, and **MSW (Mock Service Worker)** for API mocking.

## 5. Performance Testing Targets

### Endpoints needing load testing

| Endpoint | Reason | Suggested Baseline |
|---|---|---|
| `GET /chats/{id}/messages/stream/` | Each request holds an open HTTP connection for the full LLM stream duration; connection count grows linearly with concurrent users; also makes a synchronous PGVector query and then calls Anthropic API | Max 50 concurrent streams without queue build-up; p99 time-to-first-token < 2s |
| `POST /notebooks/{id}/files/create` | Writes file to disk, then dispatches Celery task; sustained upload bursts can fill disk and saturate Celery queue | 20 concurrent uploads; Celery queue depth stays < 100 |
| `POST /auth/login/` | No rate limiting; susceptible to credential stuffing if exposed publicly | Establish baseline RPS before implementing rate limiting |
| `POST /rag/query/` | Executes a PGVector cosine similarity search (`k=5`) with metadata filter; performance degrades with vector count | p99 < 500ms at 10k vectors; p99 < 2s at 100k vectors |
| `GET /notebooks/` | Returns all notebooks for a user; simple query but no pagination | Confirm still < 100ms with 1000 notebooks per user |

### Async flows needing stress testing

| Flow | Risk | Test Approach |
|---|---|---|
| Concurrent `ingest_note_task` runs | `_vectorstore_table_initialized` is a module-level flag per worker process; concurrent table-init races; also `asyncio.run()` inside Celery | Dispatch 20 `ingest_note_task` jobs simultaneously; verify all complete with `READY` status and no duplicate vector rows |
| Concurrent `POST /chats/{id}/messages/` | `order_index = ChatMessages.objects.filter(chat=chat).count()` race condition; two simultaneous requests hit `unique_together` constraint | 10 concurrent POSTs to the same chat; verify exactly 10 messages created with sequential order_indexes |
| Webhook replay under load | 50 identical `COMPLETED` webhooks for the same `payment_id` | Verify exactly one state transition; no duplicate Account saves that could corrupt subscription_end_date |

### Suggested baseline metrics

- **File ingestion**: small PDF (< 1MB) → `ingestion_status=READY` within 60s (includes partition, chunk, Gemini embeddings)
- **RAG query**: `POST /rag/query/` p95 < 1s (PGVector only, no LLM)
- **Chat stream TTFT**: time-to-first-token (first SSE chunk after request) < 2s under normal load
- **Login**: `POST /auth/login/` p99 < 200ms
- **Notebook list**: `GET /notebooks/` with 100 notebooks < 100ms

## 6. Fuzz Testing Candidates

### High priority (user-supplied input that reaches DB or external services)

| Endpoint | Field | What to fuzz | Risk |
|---|---|---|---|
| `POST /auth/register/` | `email` | Long strings (> 254 chars), unicode, control characters, `+` tags, XSS payloads in email | Email storage/display issues; `email__iexact` query performance with very long input |
| `POST /auth/register/` | `password` | Very long passwords (> 1000 chars), null bytes, unicode, bcrypt-specific inputs (72-byte truncation in some hashers) | DoS via expensive bcrypt computation on very long passwords |
| `POST /auth/password-reset/confirm/` | `uid` | Malformed base64, truncated base64, valid base64 encoding of non-UUID strings, negative numbers | `urlsafe_base64_decode` → `force_str` → `User.objects.get(pk=uid)` — type confusion on UUID field |
| `POST /auth/password-reset/confirm/` | `token` | Tokens of various lengths, empty string, all-zero token | `default_token_generator.check_token` robustness |
| `POST /notebooks/{id}/files/create` | `file` (filename) | Filenames with path traversal (`../../etc/passwd`), null bytes, very long names, no extension, multiple extensions (`file.pdf.py`), unicode filenames | `Path(uploaded_file.name).name` is used — path traversal is already neutralized by `.name`, but verify |
| `POST /notebooks/{id}/files/create` | `file` (content) | Malformed PDF (truncated, encrypted, wrong magic bytes), zero-byte file, 1GB file | `partition_pdf` in Celery task; unhandled exception sets `FAILED` but worker should not crash |
| `POST /rag/query/` | `user_query` | Empty string, 10MB string, SQL-like injection (`' OR 1=1`), prompt injection (`Ignore previous instructions`), null bytes | PGVector query with large input; prompt injection into LLM system prompt |
| `POST /rag/query/` | `notebook_id` | Non-UUID strings, all-zeros UUID, valid UUID belonging to another user | Ownership check via `get_object_or_404` — confirm 404 not 500 |
| `POST /payments/webhook/` | Request body | Malformed JSON, missing fields, extra unknown fields, very large JSON payload, duplicate `payment_id` | `json.loads(request.body)` without size limit; `data.get(...)` with None propagation |
| `POST /chats/{id}/messages/` | `content` | Empty string, 100KB string, HTML/script tags, markdown injection | Content stored and later rendered — XSS surface in frontend markdown renderer |
| `PATCH /users/accounts/me/` | `first_name`, `last_name` | HTML tags, JS scripts, very long strings (> 100 char limit), unicode | Stored XSS if names are rendered without escaping |

### Medium priority

| Endpoint | Field | What to fuzz |
|---|---|---|
| `POST /auth/google-login/` | `token` | Empty string, whitespace, 10MB string, valid JWT structure but wrong signature | Passed directly to Google API — behavior with malformed tokens |
| `GET /chats/{id}/messages/stream/` | `chat_id` URL param | Non-UUID, valid UUID of other user's chat, deleted chat UUID | Ownership + 404 behavior |
| `POST /chats/` | `notebook` | Non-UUID, UUID of other user's notebook | FK validation in `ChatCreateSerializer` |

## 7. Priority Order (Implementation Roadmap)

This is ordered by **risk × user value**: the tests that would catch the most impactful bugs if run first.

1. **`accounts` app — data exposure bug** (`AccountListAPIView` leaks all accounts). Write the failing test first. This is a P0 security bug.

2. **`payments` app — webhook handler tests** (no signature verification is a known risk; test coverage ensures the correct state machine at minimum; tests will also document the missing signature check as a gap to fix).

3. **`users` app — full auth test suite** (login, register, logout, token refresh, password reset). Auth is the gate to everything else; these tests are also a prerequisite for all other integration tests that need authenticated users.

4. **`notebooks` app — file upload + ownership isolation tests**. Confirms user A cannot upload to or read from user B's notebook, and that the Celery task is dispatched correctly.

5. **`rag` app — `ingest_note_task` unit tests** (mocking external services). The ingestion pipeline is the most complex and failure-prone part of the system; testing the status transitions and error handling here catches the `asyncio.run()` in Celery issue.

6. **`chats` app — stream endpoint tests** (message persistence, `order_index` race condition, SSE format). The streaming response is the core product interaction.

7. **`payments` app — initiate flow + ZiniPay mock**. Confirm pending payment creation and gateway error handling.

8. **`users` app — Google OAuth tests** (with mocked Google API). Less critical than email auth since it's a secondary auth path.

9. **Frontend — `useAxiosInterceptor.ts` hook tests** (token refresh and redirect on 401). This is invisible infrastructure that breaks the entire app silently if wrong.

10. **Frontend — `ChatColumn.tsx` streaming tests** (SSE parsing, markdown rendering). This is the primary user-visible interaction.

11. **`rag` app — concurrent ingestion stress test** (module-level `_vectorstore_table_initialized` flag and `asyncio.run()` under concurrent workers).

12. **Performance — `POST /chats/{id}/messages/stream/`** load test (connection holding, Anthropic API saturation).

13. **Fuzz — file upload filename + content** (`POST /notebooks/{id}/files/create`). The `unstructured` parser is a large dependency surface with many file format edge cases.

14. **Fuzz — webhook body** (`POST /payments/webhook/`). No auth on this endpoint makes it the highest-value fuzzing target for external abuse.

15. **`chats` app — `order_index` race condition regression test**. Reproduce the concurrent-write bug under controlled concurrency before the fix lands.

## Gaps & Notes

- **No test infrastructure exists yet.** The `notebooks/tests.py` file has two tests that will not pass as-written: the URL `/notebooks/create/` does not exist (correct URL is `/notebooks/`), and neither test authenticates the request user. All existing tests need to be rewritten before the new suite is added.
- **`presentation`, `quiz`, `flashcard` apps are excluded.** These apps have models and serializers but are commented out of `freshr/urls.py`. No API surface exists to test against. Test when routes are re-enabled.
- **Webhook signature verification is absent.** Until ZiniPay documents its webhook signing mechanism and it is implemented, the webhook tests should include a comment block noting this gap and a placeholder test `test_webhook_accepts_unsigned_request_SECURITY_GAP` that asserts the current (insecure) behavior and is expected to be updated when signing is added.
- **No `conftest.py` or shared fixtures.** The first engineering task should be creating a `conftest.py` (or `fixtures.py`) with factories for `User`, `Account`, `Notebook`, `NotebookFile`, and `Payment` that all tests can import.
- **Subscription expiry enforcement.** No Celery beat task flips `ACTIVE` → `EXPIRED` accounts. Test coverage cannot be written for logic that doesn't exist. This is flagged as a missing feature.
- **Database configuration for CI.** Tests default to SQLite locally but PGVector is PostgreSQL-only. Integration tests for RAG query must run against PostgreSQL. The CI pipeline needs `DB_HOST` set and the `pgvector` extension installed.
